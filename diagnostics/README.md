# 下载诊断

此脚本不修改插件文件、不触发下载、不生成签名。每次诊断最多发送 3 个详情 GET 请求，每个请求超时 12 秒。完整请求地址仅临时保存在内存，报告不包含查询参数值、Cookie、响应正文或视频标题。

## 1. 后台诊断

1. 打开 `edge://extensions` 或 `chrome://extensions`，找到 TikDownload，点击 Service Worker 检查入口。
2. 将 `diagnostics/diagnose.js` **全部内容**粘贴到 Console 执行；也可以保存为 DevTools Snippet 运行。不要在普通网页控制台执行后台诊断。
3. 保持检查窗口打开，回抖音浏览几个视频，并打开目标视频。必须在安装诊断监听之后浏览，才能记录网页请求状态。
4. 回后台 Console 执行：

```js
await tikDiag.run('7684962245634394030')
```

5. 复制脱敏报告：

```js
copy(JSON.stringify(tikDiag.report, null, 2))
```

后台会比较插件当前缓存参数构造出的请求，在默认凭据策略和 `credentials: 'include'` 下的结果。`observed` 是网页真实请求的 HTTP 状态，不代表响应 JSON 中的业务状态成功。缓存仍沿用插件的全局选择逻辑，可能来自其他标签页甚至 TikTok。

## 2. 页面诊断

1. 在 **抖音网页自身**按 F12，Console 上下文选择 `top`，粘贴同一个脚本执行。
2. 在站内切换几个视频并进入目标视频，尽量使用站内跳转，**不要刷新**，刷新会清除脚本。
3. 执行同样的 `await tikDiag.run('7684962245634394030')`，并复制报告。

页面会记录安装监听后经过 `fetch` 和 XHR 的请求。网站如果预先保存了原始函数引用，部分请求可能无法捕获；此时“没有参数”不等于网页没有发送请求。页面探测可能经过网站已有的 fetch 封装。后台、页面两份报告使用的参数及时间可能不同，因此不能把成功率差异直接当作单变量实验。

## 结果解释

| 结果 | 含义 |
| --- | --- |
| 后台默认 403，include 得到目标详情 | Cookie 凭据策略很可能是问题之一，建议重复验证 |
| 后台失败，页面取得目标详情 | 页面环境可用，应重点检查后台环境与页面结果回传 |
| 原始目标详情重放成功，重建请求失败 | 参数拼接/签名复用是重点嫌疑 |
| 网页原始请求也返回 403 | 需要继续检查网站会话、验证提示、网络环境或访问限制 |
| HTTP 200，但 `hasDetail: false` | 传输成功，业务数据仍失败；查看 `apiStatusCode`、响应类型 |
| `targetMatches: false` | 返回的详情不是目标视频，不能视为下载成功 |
| 所有探测都是 403 | 不能单凭 403 证明是签名过期或网站改版 |

`exact-observed-target-detail-replay` 只会重放实际捕获到的目标视频 GET 详情请求，不会把其他接口地址拿来请求。重放可能因时效或一次性认证失败。

当前代码中，`fetcher.js` 不读取和回传响应，`content.js` 只确认消息已转发，后台最终返回 null，这是独立的源码缺陷。报告中的 `fallbackSourceCheck` 只是对已加载后台函数的静态辅助检查，不是端到端回传测试。

完成后在两个 Console 分别执行 `tikDiag.stop()`。页面刷新或 Service Worker 重启也会清除诊断脚本。分享生成的 JSON 报告即可，无需分享原始 Network 请求、Cookie 或完整 URL。
